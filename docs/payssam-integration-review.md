# 결제선생 결제 연동 가성비 검토

> 결론: **현 시점 가성비 나쁨 — 도입하지 말 것.** 절감액(연 32~133만원 추정)이 전환 비용에 못 미치고,
> mathlab 쪽 결제 배선은 이미 완료 상태이며, para-x 멀티 프로덕트 허브 구조와 배치된다.
> 단, **재검토 트리거**(아래 §6)에 도달하면 다시 계산할 가치는 있다.

작성일: 2026-08-12 · 대상: para-x ↔ mathlab 구독 결제 레일

---

## 1. 현재 상태 — 이미 붙어 있고, 거의 끝났다

"붙일지 말지"가 아니라 **"이미 붙은 것을 갈아엎을지"** 의 문제다. mathlab 쪽 결제 배선 현황:

| 영역 | 파일 | 상태 |
|------|------|------|
| 구독 모델 | `prisma/schema.prisma::TenantSubscription` | ✅ 토스 빌링 필드(`tossBillingKey`/`tossCustomerKey`) 포함 |
| 체크아웃 진입 | `src/app/api/billing/checkout/route.ts` | ✅ OWNER 가드 + para-x 핸드오프 URL 발급 |
| 신원 핸드오프 | `src/lib/parax/handoff.ts` | ✅ HMAC-SHA256 서명 토큰 (TTL 10분) |
| 결제 통지 수신 | `src/app/api/webhooks/parax/route.ts` | ✅ 서명검증 + 멱등(`refOrderId`) + `credits`/`subscription`/`subscription_canceled` 3종 |
| 크레딧 적립·소비 | `src/lib/entitlements/service.ts` | ✅ lot 단위 FIFO 만료(약관 제6조 연동), 동시성 가드 |
| 플랜 게이팅 | `src/lib/billing/guard.ts` | ✅ 쿼터/기능 게이트, 베타 floor |
| 회귀 검증 | `scripts/verify-parax-subscription-webhook.ts` | ✅ 4개 시나리오 end-to-end |

토스 빌링 자체(빌링키 자동청구 `charge-billing`, 더닝 자동해지, `retry-grants` 재발송)는 **para-x 허브가 보유**하고,
mathlab 은 웹훅 계약만 알면 되는 구조로 이미 분리돼 있다.

즉 결제선생으로 갈아타는 비용 = 위 표의 상당 부분 + para-x 허브 측 레일 재구축.

## 2. 결제선생은 무엇인가 (사실 확인)

- **모델**: PG(전자결제대행)가 아니다. 카드사가 **직접 정산**하는 오프라인 카드가맹 구조 + 카톡/문자 청구서 링크.
  결제선생은 "데이터 전자 수·발신"만 담당한다.
- **자체 수수료**: 없음. 가입비·월정액·약정 없음.
- **건당 비용**: 청구서 발송 시 **쌤포인트 55P(55원)** 차감. API 발송도 동일.
- **카드 수수료**: 신규 카드가맹은 약 **2.2%** 를 약 6개월 적용 → 이후 연매출 규모별 우대요율 차등(영세 0.5%대).
  요율은 금융위가 정하며 전 카드사 동일.
- **자동결제**: 지원. 최초 1회 **ARS 가상번호로 고객이 카드 등록 → 빌키 발급** → 설정 주기마다 자동 청구.
- **API**: 존재(청구서 발송·포인트 충전·하위사업장 관리). 파트너사 200여 곳. 문서는 비공개 채널.
- **가입 심사**: 당일 안내, 신규 카드가맹 필요 시 최대 5일. 법인은 공동인증서 인증 필요.
- **주 고객군**: 학원·교습소. 그 외 병원·숙박·쇼핑몰 등도 사용.

## 3. 비용 비교 (Pro 133,000원/월 1건 기준)

| 레일 | 카드 수수료 | 대행 마진 | 발송비 | 건당 합계 |
|------|------------|----------|--------|----------|
| 현행 토스 빌링(PG) | 통합 요율 약 2.9~3.3% | 포함 | 0 | **약 3,900~4,400원** |
| 결제선생 (신규가맹 2.2%) | 2,926원 | 0 | 55원 | **약 2,981원** |
| 결제선생 (영세 우대 0.5%) | 665원 | 0 | 55원 | **약 720원** |

**건당 절감 약 900~3,700원.** 유료 테넌트 수별 연간 절감:

| 유료 테넌트(Pro 환산) | 연 절감 (보수) | 연 절감 (낙관·우대요율) |
|---|---|---|
| 30곳 | 약 32만원 | 약 133만원 |
| 100곳 | 약 108만원 | 약 444만원 |

⚠️ **낙관 시나리오를 그대로 믿으면 안 된다.** 절감의 본질은 *카드사 요율*이 아니라 **PG 마진(0.3%p 내외)**이다.
카드사 기본 수수료는 어느 레일이든 낸다. 그리고 온라인 PG 하위가맹점도 제도상 우대요율 대상이라,
토스 쪽 요율을 우대로 재협상하면 격차는 크게 좁혀진다. **신규 가맹 첫 6개월 2.2%는 우대 적용된 PG보다 비쌀 수도 있다.**

## 4. 전환 비용

- 결제선생 API 신규 연동: 청구서 발송, ARS 빌키 등록 플로우, 자동청구 스케줄, 결제결과 수신, 실패 더닝, 환불·해지
- para-x 허브에 **두 번째 결제 레일** 추가: 상품 카탈로그·정산 리포트·구독상태 소스 통합
- 가맹 심사 리드타임(최대 5일) + API 파트너 승인 리드타임(비공개, 미상)
- 실무 추정 **엔지니어링 1~2주 + 운영 복잡도 영구 증가**

30 테넌트 기준 회수기간 **2~4년**, 100 테넌트여도 **1~3년**. 그 사이 레일 2개를 동시 운영해야 한다.

## 5. 도입을 막는 확인 미완 리스크 (착수 전 필수 검증)

1. **🔴 업종 적격성** — 저수수료의 근거가 "**오프라인** 카드가맹 직접 정산"이다. mathlab/para-x 는 SaaS(소프트웨어·통신판매)
   업종이고 거래는 비대면 구독이다. 주력 가맹군(학원·교습소)과 성격이 다르므로 **가맹 심사 통과 여부 자체가 미확인**.
   여기서 막히면 나머지 논의는 전부 무의미 → **이 항목부터 전화 문의로 확정할 것.**
2. **🟡 셀프서브 온보딩 마찰** — 빌키 발급이 ARS(고객이 전화로 카드 입력) 기반. 웹에서 위젯 한 번으로 끝나는
   토스 빌링 대비 **가입 전환율이 떨어질 위험**. B2B SaaS 결제 UX로는 역행.
3. **🟡 구독 운영 API 공백** — 업/다운그레이드 프로레이션, 부분환불, 결제실패 재시도 정책의 API 지원 여부 미확인.
   현행 para-x 토스 레일은 더닝 자동해지까지 구현돼 있다.
4. **🟡 아키텍처 역행** — para-x 는 MathLab·ShortGEN·MathGEN 을 아우르는 **중앙 결제 허브**다.
   결제선생은 교육업 특화라 다른 제품에 못 쓴다. 레일이 갈리면 정산·환불·구독상태의 단일 진실이 깨진다.

## 6. 재검토 트리거

아래 중 하나라도 충족되면 다시 계산할 가치가 있다.

- 유료 테넌트 **100곳 이상** 이면서 카드 수수료가 실제 원가에서 유의미한 비중이 될 때
- 제품 범위가 **"학원비 수납"(학원 → 학부모)** 으로 확장될 때 → 이 경우엔 결제선생이 정답에 가깝다.
  (단 현재 기출분석 전용 트림 방향과 정면 배치)
- 원장 대상 **카톡 청구서 UX 가 전환율을 유의하게 올린다**는 근거가 생겼을 때

## 7. 지금 당장 더 싼 대안 (개발 비용 0)

1. **Enterprise 고객 세금계산서 + 계좌이체 병행.** 280,000원/월 = 연 336만원. 카드 3% 기준 고객당 **연 10만원** 수수료.
   5곳만 계좌이체로 돌려도 **연 50만원 절감** — 결제선생 전환 절감액(30 테넌트 기준)과 맞먹는데 개발이 0이다.
   B2B 한국 시장에서 세금계산서 수납은 오히려 표준이라 마찰도 없다.
2. **현행 토스 요율 재협상.** 우대수수료율 적용 여부를 먼저 확인. 레일 교체 없이 격차의 상당 부분이 사라질 수 있다.
3. **연간 선결제 플랜.** 수수료율 자체는 동일하지만 결제 횟수가 12→1 로 줄어 **결제 실패에 의한 비자발적 이탈**이 감소한다.

## 8. 만약 그래도 도입한다면 — 준수 사항

- **CLAUDE.md §0-1 준수**: 사용자 UI 어디에도 "결제선생"·"토스" 등 결제사명을 노출하지 말 것.
  결제 주체는 "구독/결제" 같은 기능명으로만 표기한다. (이 문서는 내부 기술 문서라 예외)
- 웹훅 계약(`kind`/`refOrderId` 멱등)은 현행 `/api/webhooks/parax` 규약을 **그대로 재사용**할 것.
  레일이 바뀌어도 mathlab 쪽은 수신 계약만 유지하면 되므로 변경 표면을 허브 안에 가둘 수 있다.
